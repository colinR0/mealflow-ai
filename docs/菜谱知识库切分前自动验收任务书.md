# 菜谱知识库切分前自动验收任务书

## 1. 任务目标与边界

实现一个**可重复运行的加载与质量验收程序**，判断 PDF、Markdown、TXT、JSON 来源能否转换成可追溯的父菜谱记录，再决定哪些记录具备切分资格。按将来约 10,000 份来源文件设计；当前数据用于功能验收，不能把当前小样本测试称为 10,000 份容量验证。

本任务只到“父记录与验收报告”。**不做切块、embedding、pgvector 写入、业务菜谱发布，也不让大模型补造缺失食材、用量、过敏原或步骤。**人工修订须另存修订值、修订人、依据和原文，不覆盖原始来源。

## 2. 现有数据与可复用能力

| 类型 | 当前文件 | 处理方式 |
|---|---|---|
| 结构化种子 | `data/seed/recipes.json`，32 条 | 直接按 JSON 字段读取；热量和成本为演示估算 |
| 旧版合并 JSON | `apps/web/public/data/recipes_merged.json`，937 条 | `stuff` 是自由文本；无可靠用量；部分无步骤；来源权利待核实 |
| 多格式样本 | `output/recipe-loading-v1/manifest.json` 指向 3 PDF、3 MD、3 TXT | 清单提供 9 个稳定 ID、版本、原文件摘要与名称 |
| PDF 解析产物 | `output/mineru-batch-v1/rload-001.md` 至 `rload-003.md` | MinerU Flash 文本层解析结果；是 PDF 的派生产物，不另算原始来源 |
| 外部候选 | `data/sources/pending/lin-chef-minced-pork-potato/` | `source.pdf`、`full.md`、`content_list.json`、`manifest.json`；权利未核实，保持待审核 |

已有 `apps/api/app/cli/register_recipe_sources.py` 做文件级 SHA-256 登记；`scripts/evaluate_recipes.py` 做两份 JSON 的只读质量初评。先复用其规则和问题代码，避免再写一套互相矛盾的 JSON 评估器。当前来源登记报告示例在 `output/source-registry/`，**报告文件可能过期，运行时必须重新核对实际文件摘要**。

注意：文件数与菜谱数不同。当前两份 JSON 文件含 969 条菜谱；加上 9 份多格式样本和 1 份外部待审核候选，父记录候选理论上为 979 条。实际数量以运行报告为准。

## 3. 处理顺序

1. **读取登记结果**：从文件级来源登记表或其只读 JSON 报告取得路径、格式、当前摘要。只接收明确配置的原始来源目录，不扫描整个 `output/`；MinerU 产物只通过原 PDF 的引用加入。
2. **验证来源**：检查文件存在、格式可读、SHA-256 与登记值及清单值一致。解析产物另记摘要、MinerU 版本/模式（已知时）和对应原 PDF 的摘要；无法证明对应关系时发出待核对问题。
3. **按格式读取**：JSON 直接读取字段；MD/TXT 解析标题、食材列表和连续步骤；PDF 读取已生成的 MinerU 结果。每份文件失败时记录失败并继续处理其他文件，不把解析失败当作空菜谱。
4. **生成统一父记录**：一条菜谱一条父记录。保留来源文件 ID、文件版本/摘要、源内记录 ID、菜名、份数、时间、食材原文与可确认的数量/单位、步骤序号与原文、过敏原原文、来源/授权状态、解析器版本、字段可信度及问题列表。未知字段保持 `null` 或 `unknown`。
5. **自动质量验收**：执行第 4 节规则，分别给出“可加载”“可切分”“可发布/可参与检索”的判断。可切分只表示文本结构足够，**不自动授予发布权**。
6. **生成报告与人工清单**：输出全量逐条结果、问题明细、汇总和分层抽检清单。只有在所有输出成功写完后才原子替换本次报告；失败时保留上一次完整报告并返回非零退出码。

## 4. 自动检查规则

问题至少包含 `code`、严重度（`error`/`warning`）、来源文件、源内记录、字段、原文片段及建议处理。严重度与能力判定分开保存。

| 检查 | 最低规则 | 处理 |
|---|---|---|
| 来源一致性 | 原文件/解析文件缺失、摘要不符、UTF-8 读取失败、空解析内容 | `error`；该文件不能进入切分 |
| 身份与版本 | 稳定 ID 缺失、重复、清单与解析文本冲突；版本不匹配 | 清单 ID 可作为 PDF 权威 ID，记录解析差异；不能静默改写源文本 |
| 菜名与边界 | 标题缺失/不一致；一文件含多菜但只生成一条；食材列表被连写 | `error` 或待人工核对；必须保留未拆开的原文 |
| 食材与用量 | 名称为空；数量/单位缺失、`适量`、`1个/2个`、未定义“勺” | 区分 `known`、`approximate`、`nonstandard`、`unknown`；不能参与精确份量计算 |
| 步骤 | 缺失、空白、编号不从 1 连续、步骤重复或顺序异常 | 无步骤只能做发现候选，不能作为完整做法切分 |
| 份数与时间 | 非正数、缺失、PDF 提取错位 | 保持未知；不能由模型猜测 |
| 过敏原 | 未提供或仅有未审核自由文本 | 不得当作“无过敏原”，不得启用严格过敏原过滤能力 |
| 来源与权利 | 来源不明、`license_note` 缺失或未核实、外部图片权利未知 | 保留待审核；不进入生产检索索引或 App 展示 |
| 重复候选 | 规范化名称、食材和来源线索相似 | 仅提示人工复核，不按菜名自动合并 |

针对现有 PDF 样本，已观察到 `rload-001` 在解析文本中变为 `r load-001`，食材被压成一段。验收程序应从 `manifest.json` 恢复稳定 ID，同时报告 `PARSED_ID_MISMATCH`；食材应逐项核对，不能仅凭一整段非空就判定“食材完整”。针对外部 `full.md`，步骤图说明混入“纯奶手撕吐司”，且份数、过敏原、用量、使用权存在缺口，必须保持待审核。

## 5. 稳定身份与状态设计

- 9 份自制样本使用清单中的 `rload-001`～`rload-009`，与原文件摘要一起验证。
- JSON 条目优先使用**经过唯一性验证的显式来源 ID**。当前 32 条种子没有 ID；旧版 937 条的 `bv` 存在空值和重复。因此不得把数组下标、菜名或 `bv` 单独当作长期主键。需要建立“来源文件版本＋源记录线索 → 内部稳定 UUID”的映射与冲突报告；无法稳定映射的条目保持待审核，不能静默产生可发布 ID。
- 父记录应同时保留 `source_asset_id/key`、原始摘要、源内记录线索、内部 `document_id`、内容版本、解析产物摘要。内容修改产生新版本；相同输入与同一解析/规则版本重跑，结果应幂等。
- 建议状态至少区分：`discovered`、`parsed`、`loaded`、`needs_review`、`rejected`；另存 `publishable` 与能力标志。`loaded` 仅表示成功生成父记录。

## 6. 输出契约与运行方式

建议新命令为 `python -m app.cli.audit_recipe_loading`（**此命令尚不存在，由实施者创建**）。开发库迁移尚未统一，第一版应支持从最新的来源登记 JSON 报告运行的只读模式；数据库写入须另设明确开关，并沿用项目的 schema guard。

建议输出到独立运行目录：

- `summary.json`：输入文件数、源内记录数、成功/失败数、按格式/状态/问题代码计数、规则与解析器版本、运行时间、来源摘要。
- `parents.jsonl`：每条统一父菜谱记录及字段可信度；逐行写入，不能把 10,000 份文件的全部解析文本长期堆在内存。
- `issues.jsonl`：逐条字段差异与来源引用，包含所有失败文件。
- `manual_review.csv`：固定随机种子、按来源格式/有无步骤/解析警告/重复候选分层抽样；所有 `error` 和权利未核实的来源进入待办清单，不能只抽样放行。

命令必须支持显式输入目录/清单、输出目录、`--dry-run`、规则版本和可重复运行的抽样种子。只处理内容摘要、解析器版本或规则版本变化的来源；失败记录可重试，不能把旧报告覆盖成“全部成功”。记录吞吐、失败率和峰值内存，并用合成负载单独验证 10,000 份规模；不要用 9 份样本推断容量。

## 7. 验收用例

1. 9 份多格式样本生成**恰好 9 条**父菜谱记录；ID、名称与清单一致，食材条目和步骤数逐份核对。3 份 PDF 的解析 ID 差异必须出现在报告中。
2. 两份 JSON 的 32＋937 条被逐条评估；缺步骤、未知用量、缺来源不能自动升级为完整做法、精确计算或已授权发布。
3. 外部 `full.md` 生成待审核候选，不能出现在“可发布/可检索”集合。
4. 删除一份解析产物、篡改一个摘要、制造重复 ID、断开步骤编号、混入错误图片说明，程序应分别给出明确问题并保持其他文件可处理。
5. 相同输入重跑，父文档 ID、问题代码及抽样清单稳定；只改一个文件，只重处理相关来源。
6. 定向测试使用显式 `_test` 后缀的可丢弃 PostgreSQL 数据库；若只读文件模式不需要数据库，也应覆盖路径、摘要和解析失败。不得对开发库直接运行破坏性测试。

## 8. 实施约束

遵守仓库 `AGENTS.md`，保留无关工作区改动。项目只支持 PostgreSQL；若要建表或启动 API，先核对配置的 `DATABASE_URL`，在 `apps/api/` 检查 `alembic current` 与 `alembic heads`，不能绕过启动 schema guard。当前有未完成的库存迁移，勿为本任务直接升级开发数据库。`scripts/evaluate_recipes.py` 的原有问题定义应复用或明确迁移，避免两个报告对同一条菜谱给出矛盾结论。

**交付完成标准**：提供可运行命令、自动报告、定向测试和一份实际样本验收结果；报告清楚列出仍需人工核对的记录。完成本任务后再讨论切分规则。
