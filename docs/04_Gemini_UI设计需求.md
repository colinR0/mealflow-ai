# 智慧冰箱 App · AI UI 设计需求

> 本文可整体提供给 Gemini、Claude、GPT、Google Stitch、Figma Make 等模型，用于生成移动 App 高保真 UI 和可点击原型。产品用户可见名称暂用“智慧冰箱”，不要展示 MealFlow。设计对象是中国大陆家庭用户使用的独立 Android App；品牌管理后台不属于本次交付。

## 1. 设计目标与边界

请设计一套视觉统一、信息架构清楚、能演示真实家庭任务的中文移动 App。交付不只是一个首页概念图，而是覆盖四个底部板块及关键二级页的完整原型。优先解决“查看家庭食材、理解助手结果、维护采购清单、管理家庭成员”的日常任务；避免营销落地页、复杂仪表盘和只为装饰服务的大卡片。

### 产品与实现现状

- 产品定位：高端冰箱的家庭配套 App。品牌名称、Logo 和最终品牌色尚未提供，使用“智慧冰箱”文字标识和中性临时视觉，不臆造真实厂商品牌。
- 交付形态：HBuilderX + uni-app + Vue 3 + TypeScript 的 Android App。按手机竖屏设计，桌面管理端不在本需求范围内。
- 已有四个底部入口，顺序固定为「冰箱 / 助手 / 采购 / 家庭」，默认打开冰箱。不要增加第五个底部入口。
- 用户以中国大陆手机号和密码登录；家庭数据按当前选中的家庭隔离。家庭成员可有独立用餐档案，不要求每位用餐者都有登录账号。
- 当前冰箱页已展示食材读取状态、最多 100 条已载入确认记录、数量未知状态、按已载入数据筛选，以及通往助手、采购和家庭的入口。
- 助手可提交对话任务、展示运行过程和结果、恢复中断任务，并对支持的操作展示确认卡。不要设计为助手说完即静默改写共享数据。

## 2. 全局导航与页面地图

### 底部主导航

固定四栏，图标与文字同时呈现当前选中态。底部导航在四个一级页面保持一致，注意 Android 手势区和系统安全区：

| 入口 | 职责 | 默认首屏内容 |
| --- | --- | --- |
| 冰箱 | 查看已确认食材、未知数量及冰箱服务状态；通往完整库存、未来的画面核对和其他任务 | 冰箱概览，突出真实数据状态，不把示意冰箱当成实时画面 |
| 助手 | 查询家庭食材、讨论晚餐、提出采购或偏好变更建议 | 对话起始态、常见问题和固定输入区 |

| 家庭 | 登录与家庭切换、管理用餐人员档案 | 当前家庭摘要与人员信息；未登录时显示手机号登录 |

## 3. 冰箱板块

### 定位与信息顺序

冰箱是默认首页，回答“当前家庭有哪些已确认食材、哪些数量需要核实、完整库存在哪里”。该页不是设备控制面板，也不是宣传页。首屏应让用户先看到家庭上下文和可靠食材数据；设备示意图只作弱化的产品识别元素，并紧邻“示意图，非实时画面”说明。

建议自上而下排列：

1. 顶栏：产品/页面标题、当前家庭名称或切换入口。无家庭时给出登录或选择家庭入口。
2. 冰箱服务状态区：明确显示“摄像头与识别服务尚未接入”。不显示虚构的在线、离线、最后拍摄时间或识别数量。若设计目标态画面，单独用边框或角标标记模拟。
3. 食材概览：已载入确认记录数量、数量未知数量。无法取得的指标显示“—”或不展示，不推测临期、保质期和识别待办。
4. 高频操作：搜索当前已载入的食材记录；进入完整库存；进入助手；进入采购。不要用大面积促销式快捷卡压过库存信息。
5. 已确认食材预览：显示名称、已知数量及单位，或清晰的“数量未知/待核对”，并显示确认时间。提供“查看全部库存”。
6. 底部固定主导航。

### 冰箱库存二级页（需要重点设计）

完整库存应该是冰箱模块内部的独立页面，而不是第五个 Tab，也不应只在概览页堆成很长的列表。用户从概览中的库存摘要、“查看全部库存”或搜索入口进入；二级页顶部保留返回、标题“冰箱库存”和当前家庭上下文。

首期设计为确认库存清单，建议顺序：

1. 搜索框：按食材名称筛选当前已载入的确认记录。清楚标注这是已载入记录范围，不暗示全库智能搜索。
2. 轻量筛选：优先提供「全部 / 数量未知」分段或筛选按钮。类别筛选可作为后续目标态；当前数据不足以支持的临期、过期和位置筛选不要呈现为真实可用筛选。
3. 清单行：食材名称为主；数量已知时展示数量和单位，未知时展示“数量未知”；可展示确认时间。行高适合触控，名称较长时换行，不挤压状态。
4. 空、无搜索结果、读取中和加载失败状态。失败时有明确重试入口，空库存时不伪造示例为真实数据。
5. 手动新增、编辑、标记用完、丢弃、批次、类别、位置和到期日目前不是已交付的移动端库存操作。若为完整愿景绘制这些操作，必须标记为“目标态 / 待接口支持”，并设计确认步骤，不要与已上线控件混淆。

库存记录和画面观察是不同数据：只有家庭确认后的记录才能进入“已确认库存”。数量未知必须始终与数量已知区分，不能自动估算库存足够或缺少多少。

### 识别核对目标态

设备/视觉服务接入后，冰箱概览可出现“待核对”入口。核对页展示来源画面及其采集时间，逐条显示候选食材；让用户选择确认新增、修正、忽略或更新已有记录。一次确认前应展示将写入的变化。目标态明确标记为尚未接入；当前版本不得显示虚构的检测框、模型置信度或真实摄像头画面。

### 食材详情目标态

若输出目标态详情，区分确认库存与画面观察，并标明来源、确认时间、数量状态。设备、位置、批次、存放日和到期日只有存在真实字段或明确标为示例时才展示。修改、用完和丢弃等写操作需展示影响对象与确认结果。

## 4. 助手板块

### 定位与页面组成

助手是自然语言查询和任务编排入口，面向当前选中的家庭。主界面自上而下为：页面标题及家庭上下文、简洁的起始提示、常用问题建议、可滚动任务/对话内容、贴近键盘的固定输入区。避免把欢迎语做成大型营销 Banner；对话内容应占主要空间。

建议快捷问题：

- “冰箱里还有鸡蛋吗？”
- “把牛奶加入采购清单”
- “用番茄和鸡蛋想一道晚餐”
- “家里有人不吃什么？”

快捷问题只填入或发起用户可见的请求，不应悄悄执行共享数据写入。

### 对话与任务状态

- 用户消息与助手回答有清晰区分，长回答可读、可换行。
- 任务过程使用简短、面向用户的步骤，如“查询已确认食材”“整理晚餐建议”；不显示内部推理、工具调用参数或模型原始日志。
- 展示运行中、等待确认、已完成、已取消、失败和断线恢复状态。运行中提供取消；失败提供重试或检查任务状态的明确路径。
- 断线恢复后保留已有回答、步骤和确认卡，不重复创建采购项或重复提交操作。
- 没有登录或未选择家庭时，显示引导到家庭页的空态，输入操作不可误导为已成功。
- 输入区固定在可见区域底部，适配 Android 软键盘、安全区和多行输入；发送按钮在不可发送时有清晰禁用态。

### 建议结果与确认操作

助手查询类结果应说明数据依据与限制。例如库存查询只根据当前已确认并可用的记录回答；找不到可靠记录时直接说明没有查到，不用视觉观察补全事实。

涉及共享数据修改的操作先显示确认卡，至少包括：操作名称、目标家庭、目标记录或成员、拟写入内容、数量未知等关键状态、确认/取消按钮。覆盖待确认、提交中、成功、失败、取消、过期和数据版本冲突；提交失败不得显示成功。过期或冲突时提供刷新/重新核对，而不是保留可重复点击的旧确认按钮。

当前已接入确认卡可能涉及加入采购清单、保存长期偏好。AI 生成的更丰富操作（如直接修改库存或确认整份晚餐菜单）只可作为目标态。对话默认为个人会话；家庭记录共享不代表其他家庭成员可看到用户的个人对话。

### 晚餐建议目标态

如果模型输出晚餐结果页面或对话内方案，展示用餐人数/成员、用户指定食材、家庭档案中的有效约束、每道菜使用的确认库存、缺少食材和单菜用时。标明哪些建议依据已确认库存，哪些食材数量未知或需购买。替换单道菜时保留其他菜品和已有约束。任何加入采购或保存家庭资料的动作都需先预览确认。不要声称已验证未接入的营养、医疗或过敏推断；过敏限制不明确时让用户核对。

## 5. 采购板块

### 定位与页面组成

采购是家庭共享清单的独立入口，不应只藏在助手对话里。当前实际页面已有三个状态分区：「待购买 / 已购买 / 已归档」。顶部显示当前家庭和可切换的分段控件；清单项突出名称和状态，数量状态只显示服务端真实提供的信息。

建议自上而下排列：

1. 页面标题“家庭采购清单”和一句简短上下文，不放占屏的品牌宣传 Banner。
2. 「待购买 / 已购买 / 已归档」分段导航，显示可得的条目数；无数据时不虚构数量。
3. 当前分区的紧凑列表。每条显示名称、数量已知/未知状态、当前采购状态；来源可用时才显示，并尽量保持简洁。
4. 主动添加或编辑采购项、勾选购买、撤销购买等操作属于目标态，清楚标记待开放；设计控件时保持行级操作和撤销机会，不要让误触直接改变大量项目。
5. 清单空态、当前分区为空、加载中、读取失败和重试状态。

### 购买与入库严格分开

“已购买”表示采购状态，不等于食材已经存在于冰箱库存。确认入库为单独目标流程，从已购买项发起，逐项核对实际食材、实际数量或“数量未知”、单位及可选存放位置/批次/日期，再预览将要写入的库存并由用户确认。成功后在采购项展示“已入库”或等效状态；失败时保留原状态并允许恢复。当前移动端状态修改和入库能力尚未开放，交付稿应同时给出现状和标注清楚的目标态，不要画成已接通。

## 6. 家庭板块

### 定位与页面组成

家庭页用于账号、当前家庭和用餐人员档案管理。**这里不放“我的冰箱”、冰箱库存、设备状态或冰箱内容预览**；冰箱相关内容全部属于冰箱板块。登录后家庭页的主内容应是人员信息，而不是空泛欢迎卡。

登录状态建议自上而下排列：

1. 当前家庭标题与家庭切换控件。切换后所有页面的数据上下文同步变化；明确当前选中家庭。
2. 人员信息标题和新增人员按钮。
3. 家庭成员/用餐档案列表。每张成员信息以紧凑行或轻量分组展示：姓名、常驻成员/访客、性别（若家庭填写）、过敏、长期忌口、自由描述和当前生效的特殊情况。未填写的信息不展示空白标签。
4. 每个档案提供可识别的编辑和删除操作；删除需二次确认。特殊情况显示起止日期与未开始/进行中/已结束状态，不把过期情况当作当前约束。
5. 页面底部或账户菜单提供退出登录。家庭邀请若在设计中出现，标注为待确认/目标态。

未登录状态呈现手机号与密码输入、登录中、错误提示和重试。仅支持中国大陆 11 位手机号；不设计邮箱入口。已登录但未加入家庭时，展示未加入提示、刷新或获取邀请的下一步；不要显示不存在的家庭数据。

### 人员档案编辑

用可滚动的独立页面或底部全屏编辑面板承载，不要将所有字段挤在列表卡片中。保存和取消操作固定、易触达。编辑分为三组：

**基础信息**

- 姓名（必填）、性别（可选/保密）、常驻成员或访客。
- 自由描述和备注。内容由家庭填写，不从健康事件中推断。

**过敏与忌口**

- 允许新增和移除多条限制；每项清楚标记“过敏”或“忌口”。
- 过敏使用高辨识但克制的危险提示色，并配文字标签，不能只靠颜色区分。
- 保留自然语言描述，例如“不吃香菜”。不要把偏好和医学过敏混为一类。
- 有变化时保存整份档案前显示明确结果；并发更新时提示刷新后重试，不覆盖他人修改。

**临时特殊情况**

- 支持感冒、例假、肠胃不适、康复期和自定义情况；类型仅用于家庭记录，不用于诊断。
- 每条必须可设置开始日期、结束日期、由家庭自行确认的饮食要求/标签和可选说明。
- 显示未开始、进行中、已结束。结束日期早于开始日期时阻止保存并给出就地提示。
- 不因事件名称自动生成饮食限制、药物建议、医学结论或营养疗效承诺。临时约束过期后不再作为当前推荐条件。

## 7. 状态与反馈规范

每个有数据的页面都考虑以下相关状态，不要求把无意义状态塞进同一张展示稿：

| 状态 | 必须表达的内容 |
| --- | --- |
| 未登录 | 受限功能说明和明确的手机号登录入口；不展示旧会话的家庭数据 |
| 未选择家庭 / 未加入家庭 | 说明当前上下文缺失，提供选择、刷新或下一步入口 |
| 首次空数据 | 用一句具体说明解释为何为空，提供当前可用操作；不要伪造真实记录 |
| 加载中 | 轻量骨架或局部进度，保留页面结构，避免全屏无意义转圈 |
| 网络错误 | 简洁说明、保留已有可用内容，并提供重试 |
| 权限不足 / 家庭切换 | 明确说明无法读取当前家庭，不能泄露另一家庭的数据 |
| 数量未知 | 原样显示“数量未知”或“待核对”，不替换成 0，不计算缺口 |
| 设备未接入 | 明确显示摄像头/识别服务尚未接入，不使用假在线状态、旧画面或 AI 框选图 |
| 操作待确认 | 清楚展示将要写入的内容和目标家庭，确认前不得声称完成 |
| 操作失败/冲突 | 不假报成功；保留用户输入并给出重试、刷新或重新核对方式 |
| 目标态模拟 | 在画面本身标出“目标态 / 模拟数据”，避免只在文档角落注明 |

状态文案使用简体中文和具体动词。颜色需要同时配文字或图标，不将红/绿作为唯一状态信号。成功、危险、未知和中性状态使用有区分的颜色，但整体不要只有蓝色一种色相。

## 8. 视觉与交互方向

- 设计为精致、可信、轻盈的家电配套移动 App，而非后台管理系统、聊天机器人落地页或电商促销页。
- 可以沿用浅色、清洁感和冷藏/新鲜主题，但避免全屏浅蓝渐变、重复的大圆角白卡和一层套一层的卡片。用版面分区、列表、细分隔线、局部色块建立层级。
- 冰箱主视觉应服务于当前任务：没有真实设备图像时，使用克制的产品示意图并永久标明“示意图，非实时画面”。不要用虚构食材照片冒充本家庭库存。
- 文字层级适合中文移动端连续阅读；常用操作优先使用熟悉的图标并提供文字标签或可理解的提示。触控目标至少 44×44 px。
- 页面标题、卡片标题和标签保持合理字号；长食材名、家庭名和备注可换行，不得与按钮、数量或导航重叠。
- 对话输入区、编辑面板和确认按钮适配 Android 安全区、系统键盘及 360 px 窄屏；不以视口宽度放大标题字号。
- 定义基础色板、字体层级、间距、列表行高、边框、图标风格、选中态、禁用态、提示色和动效原则。动效短促、可忽略，并尊重减少动态效果偏好。

## 9. 交付内容与验收

### 必交付页面

1. 冰箱概览：有确认库存的状态、无库存空态、未登录或未选择家庭状态。
2. 冰箱库存二级页：完整清单、数量未知标识、搜索结果为空、加载失败状态。
3. 识别核对目标态：清楚标注尚未接入，并展示逐条确认流程；不得混入当前实装界面而不加说明。
4. 助手：对话起始、任务运行、结果、待确认操作卡、失败/恢复状态。
5. 晚餐建议目标态：菜品、依据、约束、未知数量和替换单菜流程。
6. 采购：三个分区、清单空态、读取失败；另给出标记已购买和确认入库的目标态。
7. 家庭：未登录、已登录家庭、未加入家庭、人员列表、编辑档案、删除确认。
8. 特殊情况编辑：日期选择、饮食标签选择、日期错误和过期状态。

### 原型交互路径

至少打通一条现状流程和一条标清目标态的流程：

- 现状：进入冰箱查看已确认记录与数量未知 → 打开库存二级页 → 搜索一项食材 → 切换到助手查询或采购。
- 现状：进入家庭 → 切换家庭或查看档案 → 编辑成员忌口/特殊情况 → 保存并看到更新结果。
- 现状：助手发起查询 → 展示任务过程与结果；若涉及写操作，先进入待确认，不可直接显示已写入。
- 目标态：确认画面候选食材 → 加入采购清单 → 标记已购买 → 独立核对实际数量并确认入库。每个尚未实现的步骤都标注“目标态 / 模拟数据”。

### 画布与输出规格

- Android 手机竖屏，主稿按 390 px 宽度；额外检查 360 px 和 430 px 宽度。顶部状态栏、底部系统安全区和四栏导航不可相互遮挡。
- 输出页面地图、核心高保真页面、可复用组件/样式说明、空/错/加载/确认关键状态，以及能点击的原型链接或可交付设计文件。
- 使用一套虚构家庭示例数据，并在所有页面保持一致，例如“林家”、成员“小林/妈妈”、确认食材“鸡蛋/番茄”。数量未知示例必须真的写“数量未知”，不能填入推测数字。
- 不输出桌面品牌管理后台，不增加第五个底部 Tab，不把冰箱库存放入家庭页，不将“已购买”当成“已入库”。
- 设计完成后逐页检查中文文案、长文本换行、点击热区、状态差异、家庭切换隔离，以及现状与目标态标记。
