# 食材名统一规范化（从模型入库边界根治）

- 日期：2026-11-12 17:59
- 范围：`apps/api/app/services/ingredient_labels.py`（新增）、`apps/api/app/services/recipe_fallback.py`、`apps/api/app/services/web_recipe_fallback.py`、`apps/api/app/agent/durable_graph.py`、相关测试、`docs/README.md`
- 状态：已实现并通过自动化测试；未提交；未做 H5 手动点击和真机回归

## 问题与根因

现象：助手识别“芋头”时，食材名变成 `荔浦芋头、实惠新鲜）`，并原样进入：

- `食材：…`
- `缺少：荔浦芋头、实惠新鲜）。`
- `用量：…：荔浦芋头、实惠新鲜）。`
- 后续采购确认卡

根因不是展示层，而是**模型 JSON 入库边界逐字信任了 `ingredients[].name`**：

1. 联网搜索结果里的食材摘要本身是自由文本，可能带“（实惠新鲜）”等商品描述。
2. `recipe_fallback._source_context()` 把摘要原样交给模型。
3. 模型返回 `{"name":"荔浦芋头、实惠新鲜）"}`，`_parse_recipe()` 只做 `strip()`，没有拆分、剥离或校验。
4. `durable_graph` 的 `_recipe_ingredient_values()`、`_recipe_ingredient_text()`、`_inventory_analysis()` 都直接消费该字段。
5. 库存匹配失败后，该字符串进入“缺少/用量”和采购草稿。

同类入口还有网页菜谱校验：`check_web_recipe()` 直接接收模型提取的食材名列表，也可能带描述或厨具词。

## 本次决策

- 食材名是不可信输入，必须在**进入结构化数据时**规范化，而不是在页面展示时删字。
- 一个字段只保留一个食材片段；分隔符后的描述、括号说明、用量、营销词全部剥离。
- 清洗后仍含括号或分隔符、或属于厨具/非食材词的片段直接丢弃，不允许“截断后继续用”。
- 规范化在四个边界重复执行：模型 JSON 入库、忌口校验、展示、库存对比。任何新增路径即使绕过入库清洗，也不能把脏名字送进缺少列表或采购卡。

## 修改内容

### 新增 `app/services/ingredient_labels.py`

- `clean_ingredient_names(value)`：
  - 按 `、，,；;` 拆分，逐个片段清洗；
  - 成对括号说明直接移除；未闭合开括号从开括号起截断；只剩未配对闭括号的片段整段丢弃；
  - 去掉末尾用量（`500克`、`约2个左右`、`150g` 等）；
  - 去掉开头营销/加工词（实惠、新鲜、优质、精选、冷冻、去皮、切块等）；
  - 去掉首尾标点；
  - 丢弃空串、厨具/非食材词（盆、锅、碗、盘、刀、适量、少许等）和说明片段（用于、点缀、最佳等）；
  - 丢弃超过 20 字或清洗后仍含括号/分隔符的片段；
  - 同一字段拆出的多个食材去重后返回列表。
- `strip_parenthetical_notes(value)`：清洗联网摘要里的成对括号说明。

### `app/services/recipe_fallback.py`

- `_RECIPE_PROMPT` 增加约束：`ingredients[].name` 只写单个食材名，不得包含括号、产地/新鲜度、价格、促销、用量或替代说明。
- `_source_context()` 先剥离摘要中的括号说明，减少模型被污染的机会。
- `_parse_recipe()` 对每个 `name` 调用 `clean_ingredient_names()`：
  - 一个字段拆出多个食材时展开为多条；
  - 用量只保留在第一条；
  - 全空白/全描述的名字被丢弃；若所有食材都被丢弃，按解析失败处理并触发原有重试。

### `app/agent/durable_graph.py`

- `_recipe_ingredient_values()`：清洗后再做忌口校验和 key 收集；拆分字段不沿用单条 key。
- `_recipe_ingredient_text()`：`食材：` 行只使用清洗后的名字。
- `_inventory_analysis()`：库存匹配、`缺少/用量不足/数量待核对`、采购行全部使用清洗后的名字。

### `app/services/web_recipe_fallback.py`

- `check_web_recipe()` 先对模型提取的每个食材名做同样清洗，再匹配忌口；厨具词和描述不会出现在校验结果里。

- 未接入食材目录/别名解析：`荔浦芋头` 会保留为 `荔浦芋头`，不会自动归一成库存里的 `芋头`；这是名称清洗，不是同义词匹配。
- `白砂糖或冰糖` 这类“或”替代写法未拆分，仍作为一个名字参与匹配；本次只处理“附带字段”，不改变替代语义。

- 步骤文本未做同样清洗；若模型把商品描述写进步骤，可能仍出现在正文，但不会进入食材、缺少、用量或采购字段。

## 补充：第二例（未配对闭括号把说明片段当成食材）

- 补充时间：2026-11-12 19:17
- 现象：`缺少：大白菜、冬季黄心白菜最佳）、熟白芝麻、用于点缀）。`

根因：模型把括号说明拆成了独立的 `name`，但开括号在进入清洗前已经丢失，只剩 `）`。首版规则把尾部 `）` 当可剥离字符，剥离后继续保留“冬季黄心白菜最佳”“用于点缀”，于是说明片段仍然进入缺少列表。问题不在展示，而在“无配对闭括号”没有被识别为说明片段。

补充规则：

- 成对括号说明先移除；
- 只剩未配对闭括号的片段视为说明片段，整段丢弃，不再剥掉 `）` 后继续使用；
- 含“用于/用来/点缀/装饰/摆盘/最佳/最好/可选/按需/酌量/推荐”的片段视为说明，整段丢弃；
- 开头“冬季/春季/夏季/秋季/冬天/夏天/春天/秋天/当季/应季”等季节词剥离后再判断食材名；
- 最终仍含括号或分隔符的名字继续直接丢弃。

行为补充：

| 模型输入 name | 结果 |
|---|---|
| `大白菜、冬季黄心白菜最佳）、熟白芝麻、用于点缀）` | `大白菜`、`熟白芝麻` |
| `大白菜` + `冬季黄心白菜最佳）` + `熟白芝麻` + `用于点缀）` | `大白菜`、`熟白芝麻` |
| `大白菜（冬季黄心白菜最佳）、熟白芝麻（用于点缀）` | `大白菜`、`熟白芝麻` |
| `冬季黄心白菜最佳）` / `用于点缀）` | 丢弃 |
| `冬季黄心白菜` | `黄心白菜` |
