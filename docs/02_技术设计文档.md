## 2. 架构及模块边界
模块化单体API + Agent/索引worker + 独立视觉服务。先单品牌，不建多品牌平台。
- FastAPI/Pydantic：HTTP契约、输入校验。
- SQLAlchemy2/psycopg + PostgreSQL17：业务事实、事务、任务、审计。
- pgvector 0.8系列：vector(1024)，精确检索起步，锁定实际验证的补丁版本。
- PostgreSQL全文检索：jieba固定版本与业务词典预分词，simple配置，ts_rank_cd排名，不称BM25。
- LangGraph：工具循环状态与受控规划，不直接写库存。
- 对象存储：客户云私有桶，数据库保存对象key，不存大Base64。
- Redis：后续缓存/限流/通知，可丢弃；任务、事件、确认记录以PG为准。
- Vue3移动模块；视觉训练/固件由外部协作方负责。

建议新增或归并领域包：
identity、devices、inventory、procurement、knowledge、agent_runtime。
路由负责鉴权和转换，服务负责事务与业务，Provider负责供应商协议。业务服务不导入供应商SDK。
迁移阶段保留同步CRUD，统一在同步路由或受限线程执行；新Agent/检索异步I/O优先AsyncSession+psycopg，任务中每个执行单元独立Session，不跨线程/await共享同步Session。不进行长时间持锁模型调用。
参考同步与异步接口必须通过同一业务规则测试，不能各自重写限制。

## 3. 认证与授权
### 3.1 账号
联调及无品牌SSO时：邀请制本地账号、Argon2id密码哈希；服务端随机会话令牌，仅保存哈希。
同域HTTPS Cookie：Secure、HttpOnly、SameSite=Lax、Path=/；idle24h、绝对7天；登录/权限改变轮换，退出撤销。写请求检查CSRF token和Origin，明确拒绝未知来源。开发localhost允许非Secure仅开发配置。
将来IdentityAdapter校验品牌票据并换成本服务会话，不能信任前端user_id。不臆造品牌协议。
登录失败限流、邀请令牌一次性且24h过期；普通用户不能自提权。
### 3.2 家庭权限
复用workspace表示家庭，避免一次性替换全部外键；API对外称household_id，适配为workspace_id。
users保留登录身份；household_profiles新增用餐档案；memberships复用WorkspaceMember，唯一(workspace_id,user_id)。
所有访问使用AuthorizedContext(user_id, workspace_id, role)，逐对象检验归属。私聊额外检验created_by。
设备绑定、知识访问、运行、事件、确认动作均查权限。品牌管理员无家庭内容默认权限。
重要跨表关联建立(workspace_id,id)唯一键及复合外键，防止关联错误家庭。首期不把RLS作为代替应用鉴权的机制；可后续加防御层，必须专门测连接池身份隔离。
默认固定家庭ID只能用于测试种子，不可作为生产授权。
角色：owner/member；平台内容管理与运维分别授予独立权限。生产禁止默认管理员口令。

### 4.2 数量与状态
quantity_status=known/unknown；known要求quantity>=0及有效unit；unknown时quantity/unit为空，不能强制转0或1。
设备未绑可有测试媒体；生产媒体必须有受控归属。库存按批次保存；盘点存前后值，不直接删除流水。
类型变更、未知转已知等记录快照，避免用无意义数值delta表示。
菜单确认后保存recipe_id、recipe_version、约束与食材版本；不用菜名回查。
菜单状态draft/confirmed/superseded/cancelled。旧published接口在适配期映射confirmed，不引入新的食堂审批概念。
一个meal_service可先作为内部兼容餐次保留，用户端不暴露食堂术语；旧菜谱数值不可靠时标明能力不可算。

## 5. 视觉接入契约（止于观察，不实现自动存取）
### 5.1 流程
受控上传 → 校验媒体 → capture_event → recognition_job → 外部视觉服务 → observations → proposal → 用户确认。
联调来源camera_test/video_replay/image_upload/mock；真实device必须单独标记。mode=real/mock贯穿保存和UI。
使用图片或代表帧，客户端不将完整视频任意上传到正式业务。视频分析仍可留在独立研发工具。
服务端只允许从已登记对象key读取；不直接抓任意URL，防SSRF。JPEG/PNG静态图，单图<=10MB，校验解码及像素上限25MP，拒绝实际格式不符。
### 5.2 内部事件样例
~~~json
{
  "schema_version": "1.0",
  "event_id": "test-device-session-001-frame-01",
  "device_id": "device_01",
  "binding_version": 2,
  "capture_session_id": "capture_01",
  "sequence_no": 1,
  "captured_at": "2026-11-03T08:00:00Z",
  "media_id": "media_01",
  "capture_type": "image",
  "source": "camera_test"
}
~~~
device_id与认证主体匹配；workspace由有效绑定推导，不接收任意家庭归属。绑定代际不符拒绝写入。
客户端时间不覆盖服务端received_at。历史/乱序观察可留档但不能覆盖较新画面；是否最新按可信会话/序号及采集时间规则，不按到达顺序。
没有门信号使用显式联调会话，不伪装自动开关门检测。
### 5.3 视觉响应
~~~json
{
  "schema_version": "1.0",
  "job_id": "vision_01",
  "mode": "real",
  "model_version": "food-v1",
  "class_version": "classes-v1",
  "detections": [
    {"class_key":"tomato","confidence":0.92,"bbox":[0.1,0.2,0.4,0.6],"frame_time_ms":0}
  ]
}
~~~
bbox归一化xyxy，相对方向已纠正的图像；不在业务层重新镜像。未知类别保持unknown，不默默猜映射。映射版本随模型交付。
调用最多20秒、受控并发，失败保存明确状态；重试不重复生成建议。单帧无结果是正常观察，不清零。
同事交付权重/哈希、classes、manifest、阈值、测试与推理命令。暂不使用轨迹推断放入取出、重量、新鲜度。后续自动化另立需求。

## 6. 业务确认、事务与幂等
### 6.1 统一待确认动作
pending_action.type=confirm_inventory / add_procurement / receive_purchase / save_preference / confirm_menu。
payload由可信服务生成，不直接透传任意模型JSON；包含准确对象、内容和预期version；默认24h过期，显示目标对象与差异。
HTTP用户确认才是权限事实。模型说“用户确认”不能执行写入。用户单独说“好的”但没有明确action_id时要求确认对应卡片。
用户拒绝/超时不写业务；修改内容创建新版本，旧按钮失效。
### 6.2 确认事务
1. 校验用户、家庭、action归属、到期与payload_hash。
2. 按固定顺序锁动作及相关行，检查预期版本和限制是否仍有效。
3. 校验数量、单位及不为负条件。
4. 应用一次业务操作，写流水与审计，更新action状态及幂等结果。
5. commit后响应，事件通知失败可补发。
同动作重放返回保存结果；不同内容复用幂等键409；版本过期409 ACTION_STALE，重新计算并展示，不能自动批准新内容。
幂等键作用域(workspace_id,actor_id,operation,key)，保存request_hash及结果。库存来源唯一键长期有效，不能只依赖短期HTTP缓存。
### 6.3 特殊操作
采购勾选不入库；receive_purchase是独立确认，实际数量可填写，重复不增加。
相同食材仅在单位可安全换算且备注/来源保留时合并。用户已买项目不自动改。
盘点为replace_quantity，入库为add_lot，消耗为consume。unknown库存不得自动数值扣减。
长期偏好绑定明确profile；本次限制与长期偏好分开；旧upsert_owner路径迁移为pending_action。

## 8. Agent运行设计【最重要】
### 8.1 当前机制与教学边界
现有conversation.py已经有while工具循环；不要把新增一个Agent类当作重做成果。
现有graph.py是固定流程；先通过对拍测试理解规则，再替换编排，保留业务可行性。
讲清Function Calling：模型返回调用请求 → 后端校验/执行 → role=tool回填同一tool_call_id → 模型再判断。模型不直接执行函数。
### 8.2 目标图
START → load_authorized_context → understand_turn → [clarify | decide]
decide → [execute_tool → decide | validate_answer → finalize]
任务要求配餐时，decide调用compose_menu；菜单组合内部固定规则，不由LLM随意挑数值。
prepare_action → waiting_confirmation；HTTP确认经ActionService提交，再恢复图组织回执；恢复只读确认结果，不再次写业务。
需要澄清时waiting_input保存结果并结束本轮，下一用户消息创建parent_run_id关联的新运行。
finalize输出结构化结果、引用和可核实执行摘要，不输出隐藏推理。
### 8.3 State
必须可序列化：run/session/turn_id、message引用、constraints、constraints_version、事实版本快照、candidate_recipe_ids、evidence_ids、tool结果引用、menu_draft、pending_action_id、budgets、warnings。
数量以字符串、日期ISO；不要存Session、Provider、函数、回调、ORM或全部图片。RuntimeDependencies注入Provider/授权/仓储/时钟；检查点用PG Saver。
约束合并：服务器永久过敏不可移除；本轮显式限制覆盖上轮同项；未提字段保持；显式清除由受控指令表达。不要把每轮默认值覆盖成“2人/无忌口”。
同会话同一时间一个活动运行；新消息需排队或先取消，首期返回409 RUN_BUSY并提供取消入口，不并行写会话状态。
### 8.4 工具契约
registry工具条目包含name、description、Pydantic输入、effect(read/compute/prepare)、timeout、handler。
模型参数additionalProperties=false、extra=forbid；query<=500字符，候选上限服务端固定；不接收可信user_id/角色。
|工具|职责|
|---|---|
|get_inventory_summary|返回已确认、观察、数量状态和时间|
|get_member_constraints|读取本次profile及共享限制|
|search_recipes|RetrievalService统一检索，返回IDs/证据|
|get_recipe_detail|读取已发布菜谱与来源|
|check_recipe_availability|统一可用性、未知量、限制和缺口|
|get_preference_summary|明确作用域的结构化偏好|
|recommend_menu|确定性组合，返回草稿和不可行原因|
|prepare_procurement_action|预览清单写入，不执行|
|prepare_preference_action|预览长期偏好，不执行|
工具结果统一：status=ok/no_result/partial/unavailable/error，data、warnings、evidence_ids、data_versions、error_code。
非法参数结果回填模型可读错误；不把解析失败变成空参数后照常执行。
未知工具拒绝；工具输出/菜谱是数据，不得成为指令；不允许任意SQL、任意URL、自动调系统shell。
### 8.5 限制与恢复
默认最多6次实际工具调用、决策轮最多7；每次失败执行也计预算。最终回答不计工具预算。相同工具同参数同数据版本可复用本轮只读结果；权限/事实变化后不复用。
单次生成20秒，总运行60秒（不含等待输入/确认）；外部可恢复错误最多重试一次并受剩余预算限制。不可恢复参数/权限错误不重试。
精确读操作可采用规则路由，不强制每次两次LLM调用。实际费用按所有调用计。
checkpoint与业务事务不是同一原子提交；工具结果表和ActionService幂等处理崩溃窗口。恢复前检查取消、权限和事实版本。
全局模型并发初值10，工作区2，队列满503 QUEUE_FULL；正式容量依据压测调整，不当性能承诺。
### 8.6 回答校验
模型不能改结构化菜单的菜名/数量/采购项；数字由服务端结果渲染。引用只能用实际提供ID。
没有足够证据返回不足，不以LLM自评取代规则。无库存/约束读取能力时不声称安全、足够。
保留字段迁移兼容，但不保存/展示原始reasoning_content作为教学证据；观察工具事件和状态即可。

## 9. RAG设计【最重要】
### 9.1 入库
现有JSON/关系库直接构建文档，不转PDF。公共菜谱需source_id、授权状态approved、版本、能力标记。
数据清洗：食材/设备分离、番茄/西红柿别名、单位、重复变体、步骤完整性、数量与热量口径。未审核不发布。
knowledge_sources/documents/chunks/embedding_profiles/index_generations/index_jobs；documents关联recipe_id和content_version。
摘要块：名称、别名、角色、食材、方法、已知口味/设备/时间、简短做法；步骤按完整操作分组。
默认目标300～500 tokens、上限800，但以模型实际限制为准；BGE实验按其限制另切分并报告差异。每块带标题，重叠至多一个步骤。小菜谱不机械切碎。
不添加姓名、当前库存、动态价格和编造健康标签。
### 9.2 Provider与配置
EmbeddingProvider.embed_documents / embed_query；RerankProvider.rerank；独立于生成模型Provider。
默认text-embedding-v4、1024维、cosine；BGE-large-zh-v1.5、Qwen3-Embedding-0.6B做离线候选。先满足实际账号地域调用与客户许可，再使用云接口。
query/document按模型规范分别构造，固定指令和版本；校验向量数量、维度、有限数值和非零范数。
模型/维度/模板/分词/指令变化新建profile/generation；绝不用其他模型的查询向量搜旧集合。
Rerank默认关闭，先完成基线；若开发集效果提升且时延通过，再对30个摘要启用客户批准的重排服务。新供应商不通过隐式fallback混入。
### 9.3 在线检索
1. 提取明确菜名与硬过滤，别名归一化。
2. 精确命名菜谱走独立通道并校验，不被语义候选替换。
3. 向量Top40与全文Top40，查询条件含published/approved/当前版本。
4. 按父菜谱去重，各路每菜谱保留最好名次。
5. RRF = Σ1/(60+rank)，rank从1开始；同分按稳定recipe_id排序。
6. 可选重排最多30条。
7. 查菜最多8条；配餐按荤/素/汤/主食角色分别补充，最多扩大召回一次。
8. 回源取当前recipe与能力/版本，再执行本次成员限制。
全文使用预分词simple+ts_rank_cd；不能将其称为BM25。先支持精确扫描；HNSW只在实测需要时启用，过滤不足可精确补查。
不把embedding相似度当概率，不使用跨模型通用0.8阈值。接受阈值使用开发集校准并版本化；测试集不调参。
### 9.4 证据
Evidence={id,kind,source_id,recipe_id,content_version,chunk_id,excerpt,observed_at可选}。
来源页面返回允许展示的内容与链接，不能返回任意家庭数据。
做法查询优先读取完整父菜谱；缺步骤只给发现卡片，不补造原文。
semantic_score不和库存成本原始分直接相加；首期作为同业务分次级排序。
### 9.5 更新与删除
业务事务更新规范文档/全文及index_job；worker在事务外embedding，写回前核对版本。过期任务不能覆盖新文档。
查询要求chunk版本等于当前文档版本；重算期间旧向量不作为新版本证据，关键词仍可工作。
取消发布在同库立即不可见；物理删除异步。全量重建generation，回填—评测—切换—保留旧代际。
模型切换需在单事务切换完整profile/generation/阈值配置；请求固定一个配置快照。
### 9.6 评测
检索初期80条（40开发、40冻结），后续扩到240条（80开发、160冻结）；冻结集不复用来调参，避免同一菜谱模板泄漏。
类别含精确菜名、别名、模糊需求、食材设备组合、否定、无答案、授权撤销。
保存query、可接受recipe_ids、相关性0～3、must_exclude、answerable、证据。
对照字符串/全文/纯向量/混合/重排；报告Hit@5、MRR@10、nDCG@10、无答案、引用、P95和费用。
目标：可用精确菜名Top1=100%；语义Hit@5>=90%；已标注过敏漏放=0；不存在引用=0。均是验收目标，不是当前结果。
先诊断错在归一化/召回/过滤/排序/生成哪一层，再调参数。

## 10. 后台任务与SSE
job按FOR UPDATE SKIP LOCKED领取并提交租约，执行期间不持锁。租约60秒、心跳15秒；恢复领取超过租约任务，最多3次，退避后失败。
业务取消标记每个工具和写入前检查；远程请求不能保证撤回，取消后丢弃迟到生成结果，不再写业务。
agent_events按run行短锁分配递增seq；状态/工具边界立即保存，文本按200ms或256字符先到条件批量保存，不逐token写PG。
SSE：
~~~text
id: run_01:12
event: tool_finished
data: {"schema_version":"1.0","run_id":"run_01","seq":12,"type":"tool_finished","payload":{"name":"search_recipes","status":"ok"}}
~~~
事件type含status/tool_started/tool_finished/text_delta/citations/action_required/completed/failed/cancelled。
持久化后发布，客户端按run+seq去重；Last-Event-ID必须属于本run。
事件默认保留7天，过期返回410 EVENT_HISTORY_EXPIRED，前端读最终结果；不恢复已经过期的文本流。
无Redis时1秒轮询DB、15秒心跳；有Redis仅通知唤醒，不能依赖PubSub保存事件。
客户端断线不重新创建run；POST幂等键防重复提交。Nginx关闭缓冲，设置连接时限与心跳。
会话和事件先鉴权再订阅。私聊不可由同家庭其他成员枚举。

## 11. 迁移、测试与部署
### 11.1 数据迁移
先备份SQLite；验证PG空库全量Alembic链；排查batch_alter、JSON默认、bool/timezone差异。
保留既有字符串ID，不擅自全表UUID类型转换。
用餐资料复制到profiles，建立旧user→profile映射；旧demouser不变成生产可登录账号，生产账号由邀请重新建立。
原库存迁到legacy来源批次，保留数量/单位/日期；没有设备关系的库存device_id为空并提示未关联，不伪造设备。
迁移报告检查行数、金额/数量、外键、菜单、限制及重复项；不静默删除无法映射数据。
PG专用测试改显式TEST_DATABASE_URL，在临时库/唯一schema运行，启动时拒绝与生产URL相同，禁止drop_all生产。
模型单测用FakeProvider；真实模型契约测试显式开关、独立额度和脱敏测试数据。
### 11.2 测试门禁
保留原103项行为基线；更改契约时同步说明迁移，不为凑通过删测试。
新增：跨家庭/私聊/动作越权、不同profile限制、未知数量、辅料过敏、重复确认、并发消耗、绑定旧事件、worker崩溃、SSE重放、检索撤销/版本、不可信文本指令。
PG并发至少独立连接同时执行；Mock不能代替真实唯一约束/锁测试。
端到端：登录→看图→确认→问晚餐→换菜→确认清单→购买→确认入库。
### 11.3 发布
本地Compose：PG17+pgvector、对象存储替代服务、API、worker、视觉mock；Redis可后加。
客户云：私有数据库/对象存储，视觉独立CPU/GPU按实测选，API不直接执行重推理。
后端镜像带alembic.ini/migrations；迁移为独立步骤。依赖锁定、非root、密钥不入镜像；生产缺配置则启动拒绝。
开发/测试/生产数据和模型额度分离；生产不自动灌种子。
维护窗口停写/停worker→备份→迁移→冒烟→开放。开放写入后不能用旧备份直接覆盖新业务数据，应兼容回退或前向修复。
### 11.4 指标、预算与恢复
关联request_id/run_id/tool_call_id/retrieval_id/model_call_id/capture_event_id。
记录耗时、错误、tokens、费用、检索/过滤计数、任务积压、版本过期和纠错；日志不存Cookie/密钥/家庭敏感原文/隐藏推理。
cloud_ai_enabled默认false；客户批准后分开开启公开embedding与敏感生成许可，禁止一个开关默认放行所有数据。
raw_media_retention_days建议7，客户真实素材试点前批准；自动删除对象，元数据标deleted。
首轮容量测试：10k菜谱、1k模拟家庭、50普通API并发、20Agent任务/10模型并发。普通API P95目标500ms，检索P95目标3s；真实生成耗时单独报告，不能以Fake成绩冒充。
真实业务试点恢复目标RPO<=15min/RTO<=2h，需托管PG/PITR或等效方案及演练证明；未满足不可声称实现。联调环境每日备份仅代表联调能力。
单应用节点首期明确不是高可用集群。
