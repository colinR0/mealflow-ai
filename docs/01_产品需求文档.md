## 1. 产品定位与价值假设
### 1.1 定义
为冰箱品牌交付移动端业务模块及配套服务，结合设备图片、食材记录和 AI 助手，帮助家庭购物前查看冰箱、核对食材、整理共享采购，并按需推荐晚餐。
模式为 B2B2C：品牌采购与运营，家庭实际使用。首期单品牌、多家庭、多设备，不建设多品牌 SaaS。
### 1.2 核心主线
近期冰箱画面 → 食材核对 → 购物查漏 → 共享采购。
延伸任务：选择食材 → 推荐晚餐 → 局部换菜 → 确认采购建议。
首页不是聊天窗口；基础任务不强迫用户聊天。Agent 是处理自然语言和多轮任务的入口，而非替代所有按钮。
### 1.3 为什么不直接问通用助手
预期差异是已授权设备信息、家庭共享状态、结构化限制和可确认操作，减少反复描述与维护负担。不能用“用了 Agent/RAG”代替产品价值。
若识别纠错比用户原有方式更费事，应减少自动化、改善采集或收缩功能。用户活跃、节省时间、减少浪费均为待验证假设，不得填成已实现收益。

## 2. 用户与权限
|角色|可做|不可做|
|---|---|---|
|家庭管理员|绑定/解绑设备、邀请/移除成员、普通业务|访问其他家庭|
|家庭成员|查看、确认食材、采购、配餐、反馈|管理设备归属及成员|
|品牌内容管理员|审核菜谱与来源|默认访问家庭图片/聊天|
|品牌运维|查看设备/任务健康和脱敏诊断|默认浏览家庭敏感信息|

登录账号与用餐成员档案分离，儿童或老人可有档案而无账号。
家庭共享食材、清单和已确认菜单；聊天默认创建者私有。离开家庭后立即撤销相关访问。
首期联调用测试账号和测试设备。真实用户接入前必须完成真实认证、授权及隐私告知。

## 3. 交付形态与信息架构
首期移动网页模块，可独立访问并预留嵌入客户 App 的入口。原生安装包、蓝牙配网、系统推送不在本期。
四个底部入口：
1. 冰箱：首页。设备切换、最近有效画面、采集时间、食材查找、识别核对、食材记录。
2. 助手：查食材、购物建议、晚餐推荐、换菜及来源。
3. 采购：共享清单、来源、勾选购买、确认入库。
4. 家庭：成员、设备、用餐档案、偏好和隐私设置。
品牌管理端独立入口，包含设备、内容、AI质量与运行概况。
已有“代码练习”、食堂终端等无关入口从正式产品移除。下厨足迹仅保留简单反馈，完整社区/教程功能后移。

## 4. 核心术语
- 视觉观察：某时刻画面中识别到的对象，不是库存事实。
- 库存建议：从观察产生的、等待用户核对的变化。
- 已确认食材：用户明确确认的家庭记录，可数量未知。
- 数量已知：数量与单位可靠，且具备必要换算依据。
- 库存批次：同一食材的一次登记批次，可有不同日期。
- 采购建议：尚未写入共享清单的候选变更。
- 菜单草稿：待用户确认的一餐方案。
- 证据：本轮实际读取且可追溯的记录或菜谱片段。
同一会话中的轨迹编号、同类框数量、模型置信度，均不等于真实库存数量或正确率。

## 5. 功能需求
### PRD-01 家庭与设备
创建/加入家庭，登记测试设备或通过客户确认的流程绑定真实设备。家庭管理员可解绑。
绑定须验证设备持有/授权关系，知道设备编号不能直接绑定。
设备状态包括在线/离线/未知，画面新旧由采集时间表示。设备在线不能代表图片最新。
解绑后旧家庭不能获得后续画面；旧事件不能错误写入新绑定家庭。

### PRD-02 最近画面与查找
展示最近一次有效静态画面、采集时间和覆盖范围说明。
新采集失败保留上次有效画面并显示失败，不覆盖为空冰箱。
搜索“还有番茄吗”时，并列展示近期观察和用户确认记录；冲突时提示核对。
未查到回答“没有查到可靠记录”，不能回答“一定没有”。
首期不提供持续监控和历史视频播放。记录中原图过期时仍可显示来源与时间，并标记原图不可用。

### PRD-03 识别与确认
支持模型结果展示、修改类别、删除误识别、手动补录、批量确认。
用户选择“新增一批”“更新已有记录”或“忽略”，不得自动合并同类框。
数量/单位可不填写；不填保存“存在、数量未知”，不默认造一个“1份”。
不要求每次开门确认；默认不逐次发通知，进入盘点/使用相关信息时再核对。
首期仅生成建议，确认后才改变记录。取出/放入方向识别暂不深化，不列入自动化验收。
没有真实权重时可模拟联调，但页面和结果须标记模拟，不能用来验收识别效果。

### PRD-04 食材记录
字段：名称、设备、可选位置、数量状态、可选数量/单位、来源、确认时间、可选存放/到期日。
支持新增、修正、确认仍有、标记用完/丢弃。
数量未知参与推荐时标明待核对，不显示“确定够做”“准确还缺多少”。
首次批次迁移保留原有已知数量；识别不能覆盖用户最近确认的数值。
到期提醒仅依据已填写/确认日期；不从图片自动推断腐败或安全食用结论。
不要求记录每次精确消耗。用户主动填写消耗时再计算并保存流水。
反复确认、弱网重发和两人同时操作必须可预测，不重复加库存。

### PRD-05 共享采购
支持手动加入、查找后加入、助手建议、菜单缺项建议。
助手先给预览，用户确认后写入。显示来源菜谱/操作，不静默追加。
数量未知时提示核对，不自动判定缺货。
同一标准食材、可兼容单位才合并；不同规格/备注不能静默丢失。
勾选已购买不自动入库；用户另行确认实际数量、设备和批次。
已购买项目不因换菜被静默删除或修改。
首期不接电商结算，不自动选商品、价格和品牌。

### PRD-06 Agent
支持：
- “冰箱里还有鸡蛋吗”：返回证据与时间，说明不确定性。
- “把牛奶加入清单”：生成待确认动作。
- “两个人用番茄和鸡蛋做晚饭”：读取本次成员限制、查询菜谱并计算候选。
- “第二道换掉，不要汤”：保留未修改条件，局部重规划。
- “以后记住我不喜欢香菜”：预览将修改的成员与长期偏好，确认后保存。
本轮“不吃香菜”默认只作为本次限制，不默认为长期偏好。
缺少影响结果的条件才追问；人数不能用不可信客户端文本冒充权限事实。
过敏、本次明确禁止条件不能被模型或提示词放宽。
模型不可用时基础查询/编辑继续可用；业务限制不可读时不声称菜单符合限制。
不把隐藏推理文本显示为产品内容。展示执行步骤、依据、提醒和最终建议。

### PRD-07 晚餐与菜谱
首期一餐，默认两组可行候选：优先已有食材、允许少量采购。条件不足时可只返回一组或无可行方案。
条件：人数/成员、想用食材、本次禁止、口味、单菜用时、是否接受采购。
显示：菜名、来源、用到的已确认食材、观察待核对项、缺项、单菜时间及警告。
没有可信用量/价格不计算精确成本；单菜时间不代表整餐完成时间。
用户可换一道菜，不应丢失其他已确认菜品与约束。
菜谱按“可发现/可展示步骤/可配餐/可算用量/可算成本”分别审核。
无步骤记录不生成后冒充原文；生成建议与审核菜谱分开，首期正式菜单仅使用批准菜谱。
收藏/接受/拒绝反馈可以保存，首次不做自动在线训练。

### PRD-08 品牌管理与诊断
设备状态、绑定状态、上报时间、任务失败码；模型/类别版本；菜谱授权审核；汇总纠错类型、运行耗时、费用。
不将品牌运维账号默认设计为全家庭数据管理员。家庭图片诊断须受控授权和审计。
先提供页面内提醒，不承诺 App 关闭后的系统通知。

## 6. 状态与不可破坏的规则
- 建议：pending → confirmed / rejected / expired。终态不可重复生效。
- 菜单：draft → confirmed → superseded / cancelled。确认前发现事实变化则重新展示。
- 采购：待购买/已购买/已归档；入库有独立记录与唯一来源，不能仅依据勾选判断入库。
- 运行：queued/running/waiting_input/waiting_confirmation/succeeded/failed/cancelled。
waiting_input 的下一次用户回复创建后继运行；waiting_confirmation 可恢复原运行。两者都不长期占 worker。
确认内容变化、过敏档案变化、库存影响可行性变化时，旧确认失效；不能悄悄替换后执行。
用户跳过建议不影响基础查看。未检测到不删除、观察不扣减、未知不伪装已知。

## 7. 首期不做
自动存取判断、重量估算、新鲜度判定、医学营养、周菜单、供应链审批、自动支付、温控控制、多品牌运营平台、社区视频、MinerU/PDF入库。
视觉训练不是用户的职责，本项目只定义推理集成契约。模型训练成果不得冒充 Agent 开发者个人成果。

## 8. 版本与客户依赖
联调版：测试身份/设备、图片或录像、真实/模拟明确标记，完整走通观察—确认—食材—采购—配餐。
试点版：真实权限、绑定、真实模型与现场画面、移动端、监控及运行保障。
客户接入前必须确认：
1. 目标机型视角、照明、拍摄触发及是否支持门事件。
2. 设备云协议、认证、时间/序号、图片传递及重传约定。
3. 品牌账号与 App 集成方式。
4. 真实图片/档案的数据范围、保留期、云AI服务商许可。
5. 硬件/云资源、支持类别及共同验收集。
这些依赖不阻塞测试素材联调，不允许模型擅自编造客户协议。设备配网、固件开发、实际摄像头安装单独列入客户分工。

## 9. 隐私默认值
建议客户云部署，家庭图片默认不发第三方，不自动用于训练。联调只用获准测试素材。
原始静态图片建议默认保留7天，支持用户删除；这是待客户确认的部署参数，不是已获批规则。未确认前禁止真实家庭素材试点。
结构化食材记录保存到用户删除；图片过期不伪造原图可回看。注销/设备转让须撤销访问并按客户确认策略清理。
只向生成模型发送客户批准且最少必要的信息；公开菜谱可用云embedding也不等于敏感信息获准出域。

## 10. 验收映射

## 11. 产品价值验证
建议5～8个做饭家庭试用两周，对比：原有方式/通用助手、只有画面、画面+识别、再加购物配餐。
记录查找总时间（含纠错）、维护负担、漏买/重复买、主动回访、采购建议采纳、菜单采纳与放弃原因。
不要以聊天次数、页面停留或检测mAP单独当业务成功。
若AI识别未超过只看图体验，先改善视角与交互；若配餐低采纳，保持次级入口，不扩成通用聊天平台。
目标阈值在试点前冻结；文档不伪造收益、在线用户量或客户上线状态。
