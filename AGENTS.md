# Repository Instructions

## Boundaries

- `apps/api/` owns FastAPI, PostgreSQL models, Alembic, pytest, the persistent Agent, and its workers. `apps/web/` is the uni-app + Vue 3 + TypeScript Android client (Options API), not the removed Vite admin. User-facing name is 智慧冰箱; keep internal names and `X-MealFlow-Client` compatible.
- `docs/README.md` records current decisions and implemented scope. `docs/01_*`–`docs/03_*` are target contracts, not proof of implementation. `docs/开发用例/` are historical change records.
- PostgreSQL is the only supported database. API, `python -m app.worker`, and `python -m app.knowledge_worker` refuse to start unless the revision is an Alembic head (`app/db/schema_guard.py`). Never bypass that guard. Tests build tables from ORM metadata and have no Alembic history.
- Mobile reads and writes go through `/api/v2`: inventory is `inventory_lots` plus `inventory_movements`. Legacy `inventory_items` and `/api/v1` inventory stay separate and must not be exposed to the mobile client.
- Bottom tabs are 冰箱, 助手, 采购, 我的. Login is a mainland 11-digit phone number plus password. One `user` role; household membership and personal sessions are still checked separately.

## Commands (PowerShell)

- This Windows machine uses the Conda `mealflow` interpreter: `D:\APP\miniconda3\envs\mealflow\python.exe`. The repository `.venv` is Python 3.14 and lacks API dependencies; do not use it for backend work.
- Install backend/dev dependencies from the repo root: `& 'D:\APP\miniconda3\envs\mealflow\python.exe' -m pip install -e ".\apps\api[dev]"`. Local embeddings are the extra `local-embeddings` extra.
- From `apps/api/`, check `alembic current` and `alembic heads` before `& 'D:\APP\miniconda3\envs\mealflow\python.exe' -m alembic upgrade head`. `alembic.ini` has a URL, but `migrations/env.py` overrides it with `DATABASE_URL`.
- Run API and the Agent worker in separate terminals from `apps/api/`: `& 'D:\APP\miniconda3\envs\mealflow\python.exe' -m uvicorn app.main:app --reload --port 8000` and `& 'D:\APP\miniconda3\envs\mealflow\python.exe' -m app.worker`. API startup starts neither worker.
- Knowledge rebuilds are queued, not run inside a chat turn: `scripts/rebuild_rag_index.py --enqueue`, then `& 'D:\APP\miniconda3\envs\mealflow\python.exe' -m app.knowledge_worker --once` with `apps/api` on `PYTHONPATH` when launched from the repo root. `scripts/cleanup_rag_generations.py --keep 1 --apply` drops inactive ready generations.
- Run backend tests from the repo root with `MEALFLOW_TEST_DATABASE_URL` pointing at a disposable PostgreSQL database whose name ends in `_test`; `tests/conftest.py` aborts otherwise and drops/recreates all ORM tables per test. Example: `$env:MEALFLOW_TEST_DATABASE_URL='postgresql+psycopg://mealflow@127.0.0.1:5434/mealflow_s7_test?gssencmode=disable'; & 'D:\APP\miniconda3\envs\mealflow\python.exe' -m pytest apps/api/tests/test_inventory_lifecycle_api.py -q`. Never point it at a development or demo database.
- Backend lint from the repo root: `& 'D:\APP\miniconda3\envs\mealflow\python.exe' -m ruff check apps/api`.
- In `apps/web/`: `npm ci`, `npm run typecheck`, `npm run build:app-android`. CLI output is `apps/web/dist/build/app`, not a signed APK. Component tests are plain Node: `node --test tests/*.test.mjs`. H5 dev server: `npm run dev:h5` on port 5173, proxying `/api` to `http://127.0.0.1:8000` unless `MEALFLOW_API_PROXY` is set.
- `docker compose -f docker-compose.s7.yml up --build` is a local integration stack (PostgreSQL, migrations, API, worker), not the uni-app client. It needs `MEALFLOW_LOCAL_DB_PASSWORD` and publishes the API on `127.0.0.1:8003`.

## Non-obvious Constraints

- `Settings` resolves `env_file=("../../.env", ".env")` relative to the process working directory, not the repo root. Start API, Alembic, and pytest from the repo root or `apps/api`. `.env` is git-ignored; never commit credentials.
- Tests force empty LLM keys and replace providers with fakes. Do not "fix" tests by calling a real model. Default runtime retrieval is `demo` plus fake 64-dimensional embeddings. Native search uses `BAAI/bge-small-zh-v1.5` at 512 dimensions with the BGE Chinese query prefix; a mismatched provider, profile, or dimension must refuse retrieval. `RETRIEVAL_MIN_SIMILARITY` (default 0.41) filters recall only.
- Recipes and cooking skills are vector chunks. Substitutions, flavor templates, and risks are typed SQL on `approved` rows only (`search_stage=typed_lookup`): no vectors and no RRF. `recipe_import` catalog rows stay out of household ingredient suggestions.
- `KNOWLEDGE_WEB_SEARCH_ENABLED` defaults off and is independent of `RECIPE_WEB_FALLBACK_ENABLED`, which defaults on. Named-dish fallback is local RAG, then a recipe-site summary or model fill, at most two dishes per turn. Skip the web when no model is configured or time is short, and do not invent ingredient keys.
- The model chooses the tool from the user utterance. `answer_stock`, `answer_named_dishes`, and `answer_restricted_food` then render the reply: stock existence, the named-dish recipe with its procurement card, and registered allergy or dislike directions. Do not put a keyword gate in front of that model call. Direct “还有 X 吗 / 有没有 X” answers still come from active lots: a row means 有, unknown quantity means 有，数量待核对, and no row or a known quantity of 0 means 没有. Do not answer those with 无法确认. “够不够、缺什么、怎么做” still goes through the model’s other tools.
- Canonicalize ingredient names at model-JSON ingest, display, restriction checks, and inventory comparison. Split on separators, strip brackets, amounts, and marketing words, and drop utensils and non-food fragments. Discard a name that still contains brackets or separators.
- A named dish that is missing ingredients, or short on known stock, produces one batch `add_procurement` confirmation card. Card quantities stay unknown; show the recipe amount and current stock when short. Unknown stock does not enter the draft. Confirmation writes pending procurement only, never inventory. Other shared writes also need an explicit confirmation step before side effects.
- Inventory quantities are `known` (quantity + unit) or `unknown` (both null; never infer 0 or 1). PATCH, consume, and remove require `expected_version`. Only `active` lots may become `consumed` or `removed`; repeated or cross transitions return 409 without new movements.
- Cooking logs are visible to the household; only the creator can edit them. The assistant ignores them unless that creator opts in with a `log:<id>` citation. Photo bytes are local (`data/cooking_photos`); production object storage is not wired.
- Device images, YOLO, and climate data are not connected. Keep those empty states empty, and do not treat recognition as confirmed stock.
- Native clients authenticate with Bearer sessions marked `X-MealFlow-Client: native-app`. Browser sessions use cookies, and writes require CSRF. Preserve both paths when touching auth or CORS.
- Keep frontend and backend code concise. Add checks only at real boundaries. Use `try/except` or `try/catch` only for recovery, translation, cleanup, or user feedback, with a short comment when the reason is not obvious.
- Check `git status` before editing and preserve unrelated in-progress changes.
- Development records are optional. Before each development or modification task, ask `本次开发/修改是否需要填写开发记录？` (or `Should this change be recorded in the development records?`). Create one only when the user agrees for that task. Then add `docs/开发用例/YYYYMMDD-HHMM-brief-change-name.md` in the same change (sequence suffix on collision) with date, scope/files, behavior, verification results, and known gaps. Never overwrite or rename earlier records.
- When a task explicitly uses Agent1 for implementation and Agent2 for testing, run exactly: Agent1 implements, Agent2 tests and documents findings, Agent1 makes one fix pass from that report, then stop. Do not start another test/fix cycle. Report remaining findings as unresolved.
